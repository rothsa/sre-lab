Did the Agent Do It Right?

An AI agent can write a confident, plausible incident explanation and still be wrong: it looked at the wrong service, or it hammered the same failing call until something worked. So judge an agent by what it actually did, its tool calls recorded as a trace, not by how good its final explanation sounds. Pick an incident and compare three runs.

How it's checked

Each tool the agent can use (get_metrics, search_logs, list_deploys and the one tool that changes something, rollback) records an OpenTelemetry span when it runs: the tool name, its arguments, a summary of the result, ok or error, and how long it took. The span names and the gen_ai.* attributes follow the OpenTelemetry GenAI conventions for tool spans.

Span-based evaluation means the checks read that trace instead of (or as well as) the final answer. Pydantic Evals runs every case (incident × run) as a task, captures the spans each task produced into a span tree, and hands it to the evaluators. A built-in HasMatchingSpan asks "is there a span like this?"; custom evaluators can walk the whole tree in order.

From the build script

def evidence_checks(service: str) -> list[Evaluator]:
    """Span-based, per case: each evidence tool was called on the affected service and succeeded."""
    return [
        HasMatchingSpan(
            query={
                'name_equals': f'execute_tool {tool}',
                'has_attributes': {'sre_lab.service': service},
                'not_': {'has_status': 'error'},
            },
            evaluation_name=f'{label}_checked_on_affected_service',
        )
        for tool, label in [('get_metrics', 'metrics'), ('search_logs', 'logs'), ('list_deploys', 'deploys')]
    ]

The whole script, agent-evals/build/run_evals.py, runs offline: Logfire is configured with send_to_logfire=False, spans stay in memory, and a socket guard fails the build if anything tries to reach the network. Its output is results.json (what this page shows) and the plain-text pydantic-evals report.

Honest limits

  • The checks only see instrumented tools. A call that doesn't record a span, or a span without its arguments, is invisible. In the OpenTelemetry conventions, tool arguments and results are opt-in attributes because they can be sensitive, so a real trace may not contain the service name these checks rely on.
  • Passing sample cases doesn't establish real-world reliability. Nine scripted cases show what the checks catch; they say nothing about how often a real agent goes wrong on incidents nobody wrote down.
  • Detecting excessive calls after the run doesn't prevent them. The retry loop below already spent its calls (and in one case 40 seconds of timeouts) before any evaluator looked. Enforce call budgets, rate limits and approval for changes like rollbacks at runtime, in the tool layer.
  • Eval harnesses have bugs too. An October 2026 audit of one agent benchmark found a reward-function defect that changed the environment state before post-run scoring. Another study found that tests which reproduce a bug can still accept an incorrect patch. Audit the oracle before trusting a score. ProgramBench now scores only its expected tests and drops tests a submission wrote itself (12 October 2026).
  • A model swap can change the API, not just the answers. Gemini 4 Argon (GA 13 October 2026) ignores temperature, top_p and top_k, so an eval that fixed those settings no longer tests what it says. Pin model IDs and rerun the evals on every swap.
  • A judge can believe the agent. An October 2026 paper on agent verification notes that a judge may accept unsupported claims, "including an agent's own reports of success"; its verifier checks the environment state and the execution trace instead. These checks read spans for the same reason, not the agent's summary.
  • Reports drop what a reviewer needs. In CTXGAP (October 2026), readers of an agent's reports recovered 52.0% of task-state facts, against 92.7% for readers of the full execution context. Check the trace when it matters.
  • A judge's "first mistake" is often not the cause. Four frontier judges labelling failed agent runs agreed on the exact step in only 21 of 57 cases, and flagged mistakes in successful runs; restarting from a measured point helped where restarting at the judge's label did not (October 2026).
  • The grader can be gamed too. When Anthropic trained an auditing agent with reinforcement learning (15 October 2026), rewards that scored each investigation on its own were reward-hacked: "the auditor learns to manufacture alarming findings". Having a judge compare two investigations of the same target held up better, and adding benign targets with nothing planted kept false positives down.
  • A guard model can be talked out of it. Datadog Security Labs (15 October 2026) put counterfeit "policy" text ahead of attack content, and Jev, a classifier LangChain uses to gate risky tool calls, mostly stopped flagging it; plain injection did not work. Keep untrusted text away from a judge's instructions, and back model guards with hard limits in the tool layer.
  • A grader that reads only the summary fails good runs. Google Cloud's plugin team (16 October 2026) found a judge reading only final replies failed 3 of 11 prompts that the tool-call logs showed had passed: "The grader penalized the agent for doing the right thing simply because it didn't brag about it in the summary." A flattened event list also hid parallel tool calls, so keep the turn structure.
  • Judges drift. Netflix (14 October 2026) sends a weekly sample of passed and gated outputs to human raters, re-tunes the judge's rubric when it falls behind them, and has a human approve every change: "An LLM judge must never operate alone."
  • Read the transcripts, not just the score. Preference Model's audit of Terminal Bench 4 (19 October 2026) found that 44 of 65 tasks could be passed by cheating. In one, a model exploited a gap in the grader: "It got full marks, and its final methodology report never mentioned the teleporting."
  • Score the artifact, not the steps. NVIDIA and Siemens (14 October 2026) gate a chip-design agent's final files on coverage, validity and integrity checks, and "The reward is zero if any gate fails."
  • Measure recall, not just precision. Steve Yegge's own evals (October 2026) found two models about equal on specific tasks, but on open-ended tasks one "correctly spots and acts on important issues more often".
  • Benchmarks lose their human baseline. Ofir Press, a SWE-bench author, wrote (13 October 2026) that SWE-bench "has gotten pretty saturated at the frontier" and that the next benchmarks target tasks that would take a team of engineers years.
  • Isolate each task. An agent can pass an eval "by tampering with tests or overwriting the file that records its score". Docker's Harbor integration (October 2026, on the nightly release) runs every task in a microVM with its own kernel, and lets a task download dependencies during setup, then restricts internet access while the agent works.
  • Synthetic data. The incidents, services, results and timings are made up, and the agents are deterministic Python functions, not models. The output checks use simple keyword matching that suits this fixed data and would be too weak for free-form answers.
