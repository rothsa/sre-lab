Do We Still Need PRs?

Agents now open more changes than people can read. Some teams have dropped pull requests and push to main. Others say review matters more than ever. This page sorts out what a pull request actually does, what each side gets right, and what an org with hundreds of teams should run instead. Every claim links to its source.

Research write-up · as of 29 October 2026

Bottom line: keep the jobs, drop the mandatory read

A pull request does four jobs at once. It catches mistakes before they land. It records what changed and why. It is where people learn the code and agree on direction. And it is the approval an auditor looks for. Agents broke the first job. When agents open more changes than people can read, a rule that a person reads every diff turns into stamping.

The other three jobs still matter, and none of them needs a person on every diff. So I run one lane policy for the whole org. A classifier and CI put each change in a lane by path and risk. Low-risk changes land behind checks and get sampled after. Risky paths need a person to review the intent, and the riskiest need two. An agent's approval never counts as a person's. Every commit links to the request and the agent run that made it. Each lane has a revert rate, and a lane whose rate climbs gets tighter.

1A PR does four jobs, and agents broke one

Review was never only about bugs. In Google's study of its own code review, developers said they expect "education", plus "maintaining norms, tracking history, gatekeeping, and accident prevention. Defect finding is welcomed but not the only focus" (Sadowski et al., 2018). John Allspaw put it in agent-era terms: "code review is also a coordination process, a sensemaking process, and a governance process" (Adaptive Capacity Labs, 24 Aug 2026).

The gate is the job under load. At Imprint, "The p50 pull request review took about 33 minutes to complete 2 years ago, but now takes us about 77 minutes" (Will Larson, 17 Oct 2026). DORA's 2025 report found AI adoption helps throughput but "does continue to have a negative relationship with software delivery stability" (DORA, Sep 2025). And the human gate was leaky before agents. Intercom looked back at its outages: "those product changes that did cause outages in the past? They were all reviewed and approved by humans" (Intercom, 21 Apr 2026).

So the useful question is where each job goes when a person no longer reads every diff.

Catch mistakes before they landA check that runs on every change and can't be skippedCI that blocks, tests, an independent review agent, a risk classifier that picks who else must look

2The case for dropping PRs

Amp is the clearest example. Thorsten Ball (13 Oct 2026): "No pull requests, no code review. We push to main. Our agents read production logs, watch deploys, grant feature flags, and check their own work end to end" (X). Amp's SOC 2 write-up says "Skipping pull requests was a deliberate choice from the first commit." Its controls are restricted push access, verified signatures on main, CI that blocks main, and "Commits link to the Amp threads that produced them" (Will Dollman, Amp, 13 Aug 2026).

The argument has two parts. First, PRs were never the point of CI: "CI means continuous integration and its original meaning is the opposite of having long-lived branches and PRs" (Ball, 16 Oct 2026). Second, proof beats a diff. Amp agents record a video of the feature working, and Ball asks "how differently do you approach a code review if you know there's video proof that it works?" (13 Oct 2026). By 21 October he wrote "Mandatory code review as we've known it is over" (X).

Others went the same way. Zed "disabled pull requests on Delta's own repository" and replaced them with the Delta thread (Nathan Sobo, 16 Sep 2026). DHH: "there's no future where you're manually reviewing every line of agent code" (28 Sep 2026). Geoffrey Huntley closed pull requests on his open-source project (14 Oct 2026).

Two caveats. Amp itself says it is "not going to pretend a 2,000-person company should let everyone push to main." And most of the loudest voices sell an agent or a forge: Amp, Zed, and Entire, whose founder Thomas Dohmke wrote that "The pull request has become an audit log that only the agent reads" (Entire, 26 Oct 2026). Read the practice, and discount the pitch.

3The case for keeping review

The strongest case is about what a reviewer notices that a checker can't. Allspaw: "The agent reviews what is there; engineers with expertise can easily notice what's missing," and when a reviewer is confused, "their confusion is the finding." A test suite passes on what it tests. A person who knows the system sees the error handling that wasn't changed.

The second case is about who counts. Anthropic's Claude Code team lets automated review clear low-risk changes, "but it can't fill a slot that calls for a human," and "An agent's approval never counts as a person's, either" (claude.dev, 15 Oct 2026). That keeps separation of duties real when an agent writes the code and another agent reviews it. It is the same reason the fleet ladder asks for a verdict from a different model family than the author.

The third case is a warning about fake review. Larson describes teams reviewing with local harnesses and pasting the comments back, "meat proxy review", which he calls "a bottleneck-pretending-to-be-a-solution." Keeping a mandatory read that nobody really does is worse than either side's answer. It slows everything and proves nothing.

4Where they meet: lanes set by risk

The teams with the most agent volume landed on the same design. A change goes into a lane by what it touches, checks decide most lanes, and people move to the two ends of the work: agreeing on it before agents start, and reading what landed.

  • Anthropic, Claude Code team (15 Oct 2026). "The change sets the tier, not the author. A classifier reads the change and picks its risk tier." Low risk needs no human "once automated review and security checks are green"; ordinary changes need one person; the highest-risk paths need two. "Some paths always need a person, anything owners have listed as sensitive and any CI workflow file." On an agent-written PR "the person directing the agent counts as one of the required reviewers," and "An approval covers one specific commit."
  • Imprint (Larson, 17 Oct 2026). A small-change lane CI enforces: under 1,000 lines, no p1 or p2 findings from the AI review bot, an author with 10+ merged PRs in that service, shared libraries excluded, and a per-path .small_change file. "About 10% of changes qualify."
  • Anthropic, source control (13 Oct 2026). "Our team members still review every change request for the system, but they now examine the intent of the change." They also found "A proper merge queue, for example, doesn't make much sense at agent scale," and put the effort into post-merge and pre-deploy testing (Anthropic).
  • Intercom (21 Apr 2026). "over 19% are auto-approved with no human reviewer in the loop," with the review agent refusing changes that are too big, and its auditor Schellman checking the process against SOC 2, HIPAA and ISO 27001, among others.
  • Huntley (29 Oct 2026). His diagram of what he has been building: two people agree on a story, it fans out to a hundred agents in their own sandboxes, and every change goes through one submit queue and a risk classifier. Low risk lands, then gets "review after land" with feedback as a follow-up diff. High risk waits for a person. He calls it "the shape of CI/CD, code review, and ultimately what displaces GitHub itself" (X). The full write-up isn't out yet.

Amp fits the same shape at its size. Its review is the agent's own end-to-end checks plus a link from every commit to its thread, and people still look where the risk is: "We do review high-blast-radius code, but we certainly don't review everything agent puts out" (Ball, 29 Sep 2026). The no-PR camp and the keep-review camp disagree about the default lane. They agree that the lane, not the author's seniority or the team's habit, should decide who looks.

5What the auditor asks for

"Compliance needs PRs" is the most common reason given for keeping them. For SOC 2 and NIST change control it doesn't hold. Amp's SOC 2 write-up: "SOC 2 doesn't require pull requests." On the list of what it does require, "code review isn't on the list." NIST SP 800-53 asks you to "Review proposed configuration-controlled changes to the system and approve or disapprove such changes" (CM-3). That is approval of a change with a record. It doesn't say a second person reads the diff.

What binds you is the set of controls you wrote down, plus any framework that names code review for the systems in its scope. Larson: Imprint's compliance obligations "today require that an independent human reviews changes in a subset of our repositories," and those obligations "can be changed." Intercom took its auto-approval design to its auditor before relying on it. So the order is: write the lanes into your documented controls, agree them with the auditor, then turn them on. The trail is the commit, its signature, the linked run, the lane it took and who approved it.

6Running it across hundreds of teams

At org scale the PR question is a policy question. If every team picks its own answer, you get a few teams pushing to main with weak checks and many teams stamping PRs nobody reads. The platform owns one lane policy instead.

  • One policy, set by path. The lane comes from what a change touches and how risky it is, not from the team. Paths like CI workflows, auth, billing, infrastructure and shared libraries are always in a human lane. Teams can tighten their lanes and can't loosen them. The policy is versioned and reviewed like code. Ownership data says who the person in a human lane is (see Ownership).
  • An agent never fills a human slot. Agent review is a check. The person who directed the agent counts as one reviewer, as on the Claude Code team, so a two-person lane needs someone else. Approvals cover one commit, so a later agent push needs a new one.
  • Every change carries its record. Signed commits, a trailer linking the request and the agent run, and the lane it took. That record is the audit trail, and it is where a person goes to learn why the code looks the way it does.
  • People move to the ends. Review the plan or story before agents fan out, because a bad plan costs a hundred changes. After changes land, sample the low-risk lane and read it, and send feedback as a follow-up change.
  • Each lane has numbers. Per team and per lane: share of changes, revert rate, change failure rate, and wait for first review. A lane whose revert rate climbs tightens. A human lane whose wait keeps growing is a sign that more of its paths could move down a lane safely.

So do we still need PRs? We don't need a rule that a person reads every diff. We do need the gate, the record, the shared understanding and the approval. A large org gets them from a lane policy, a record on every commit, and people who spend their attention where the risk is.
