Step 2 of 9

One canonical event, not 20 fragments

Core org schema (JSON / logfmt)

{
  "service.name": "checkout",
  "severity": "ERROR",
  "message": "card charge timed out",
  "trace_id": "4bf92f3577b34da6",
  "user_id": "u_94821", "duration_ms": 1840
}

Why wide events win

One rich line per requestmaps cleanly onto OTel Logs data model
Instead of 20 scattered linesno stitching fragments during an outage
Humans & agents query every team the same way
Step 3 of 9

Keep labels tiny; put IDs in metadata

Indexed labels (short allowlist)

teamnamespaceappenv
Each unique label set opens a separate Loki stream. Keep values in the tens.

Structured metadata (unindexed)

trace_iduser_idrequest_idpod
Queryable after stream selection without exploding stream count or index size.

Keep active streams under 100k

Ingesters flush compressed chunks to object storage

1 stream = 1 chunk chaincompressed in memory, flushed to S3
Index maps labels → chunkslog body text is never indexed
Too many streamstiny chunks + huge index + slow reads

Grafana sizing rule for large tenants

Healthy ceiling: < 100,000 active streams Keep shard_streams on for hot streams
