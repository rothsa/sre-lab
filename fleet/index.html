One Agent to Hundreds

Running hundreds of coding agents is not one agent times a hundred. Each jump in scale breaks something the smaller setup got away with: your review time, shared files, one coordinator's attention, then rate limits and cost. Step up one stage at a time. Each stage says what to add, what breaks without it, and how to tell you're ready for the next. Then an org layer on top shows how a company runs many of these ladders at once: one platform, team budgets, pooled limits and an audit trail.

The main thread is pstack, Lauren Tan's published agent workflow, alongside what Stripe, Spotify, Uber, Cursor and Anthropic publish about their agent fleets and how Mitchell Hashimoto, Dex Horthy and Boris Cherny describe their own ramp-ups. Stage sizes are teaching breakpoints, not thresholds from a study.

              Fast inside, careful at the edges

              Most real codebases are not greenfield all the way down. New code can run at fleet speed, but where it meets older systems, every change needs a slower lane. The people above handle that split the same way.

              • Build the harness into the new code from day one. Böckeler: greenfield teams can bake it in, while legacy teams face the harder problem, because the harness is most needed where it is hardest to build. (martinfowler.com)
              • Add tests at the boundary before you add agents there. Where Spotify's repositories had no build-time tests, its agent couldn't verify its own work and the owning teams had to. (Spotify, Honk Part 4)
              • Make the agent flag what needs judgment. Spotify had Honk leave those fields unchanged, with a comment linking to the human migration guide, so the reviewing team saw exactly where to look.
              • Review the plan for anything that crosses the boundary. A wrong idea about how the old system works is cheapest to catch in a short plan, before it becomes thousands of lines. Then read the code, a slice at a time. (Horthy 2025, 2026)
              • Fix locally, then spend CI sparingly. Stripe's rule for a codebase of hundreds of millions of lines: often one, at most two CI runs, after everything local passes. (Stripe)
              • Standardize before you scale. Spotify's conclusion after migrating about 1,800 pipelines: the next large migrations depend on consolidating and standardising what the agents touch.
              • Put shared gateways between agents and internal systems. Uber describes a central model gateway (workload identity, PII redaction) and an MCP gateway for tool access, so every agent goes through the same controls. (Uber talk)
              • Map zones before agents work. Green code gets a tight agent loop, yellow gets characterization tests first, red gets a human on every step; pin current behavior in a separate pass so the agent doesn't write the tests that grade it. Autonomy should follow blast radius, observability, and recoverability. (Addy Osmani, Sep 2026)
              • Decide the evidence and the review tiers before the run. Anthropic's modernization guide has each change carry evidence that can be checked without a human, then tiers human review by blast radius and agent confidence. (Anthropic, Sep 2026)
              • Don't let a summary stand in for the old code. Microsoft's COBOL-to-Java sample turned off feeding extracted business logic to its converters by default, because they followed the summary instead of translating the COBOL. (changelog, Oct 2026)

              How the pieces fit

              Across the stages, the human's job moves from doing the work to writing briefs, then to reading verdicts, then to answering only the questions no experiment can settle. pstack's Orchestrate playbook describes the end state as the human checking in twice a day instead of every five minutes. Irreversible actions (force-pushes to shared branches, deploys, data deletion, customer messages) still wait for a person.

              The ladder sits one level down inside the org layer. Each team climbs the five stages at its own pace. The org owns what the teams share: the platform and gateways, an identity per agent, each team's budget and quota, the pooled API and GitHub limits, the audit trail, and one fleet number that puts merge rate next to change failure rate.

              Two ideas carry the whole ladder. First, evidence, not assertion: a worker's "done" counts only with the evidence its brief asked for. pstack's swarm skill drops a report missing its SHAs, respawns the worker once, and records a second miss as a gap: A gap does not count as a pass. Second, encode lessons in structure: a correction you keep repeating becomes a lint rule, a check or a script. pstack's principle puts it bluntly: The instruction is the symptom.

              Memory is the newer layer. In her AI Native DevCon talk, Anthropic's Lamis Mukta describes memory moving from CLAUDE.md files to skills to plain files that agents search with ordinary tools. It then needs versioning, a hash check before every write, and read-only organisation-wide memory beside writable per-agent scratchpads once many agents share it. "Dreaming" is a separate batch job that reads past sessions and proposes a cleaned-up memory store for a human to accept or reject. Claude Managed Agents documents the same mechanics (immutable memory versions, a content_sha256 precondition on writes). Dreams are in research preview.

              When more agents pay off. A Google Research, Google DeepMind and MIT study of 260 agent configurations found that tasks where one agent already succeeds more than 45% of the time experience negative returns from additional agents, as coordination costs exceed diminishing improvement potential. On SWE-bench Verified, each multi-agent architecture did slightly worse than one agent on average across models (−15% to −2%), though some weaker models gained, and each result rests on 20 tasks. A September 2026 preprint, AsynCodeBench, adds that better coding performance does not necessarily translate into stronger collaboration between agents (arXiv:2609.32662). An October 2026 study on ProgramBench found that teams beat solo agents but cost three to seven times as much; planning was the most valuable use of extra workers, and a mixed 17-agent team came within 1.4 points of a strong 5-agent team at 70% lower cost (arXiv:2610.17471).

              Newer results point the same way. Vals AI found agent teams cost 1.8 to 5.1 times as much as single agents, with only one of four score gains statistically significant (Oct 2026). A ProgramBench preprint found the best use of extra agents is planning: planners keep improving as the team grows, while implementers and verifiers plateau beyond four workers (arXiv:2610.17471). Toby Ord's reading of OpenAI's published swarm charts: The most important answer is speed, bought with extra compute (Sep 2026; a secondary analysis). Anthropic's agent-building guide starts from one loop with skills and tools, and keeps a subagent only if the folded version scores worse on an eval (Oct 2026).

              Scale pays when the work splits into independent pieces and each piece has a check the agent can't fake. Anthropic's C compiler run used 16 parallel agents. It stalled when every agent hit the same kernel bug, and recovered once GCC served as a known-good oracle. (Kim et al., arXiv:2512.08296 v3; Anthropic: Building a C compiler with a team of parallel Claudes)

              Honest limits

              • The stage sizes are illustrative. 1, 3, 10, dozens and hundreds are where the cited sources describe things breaking (worktrees, about ten agents per coordinator drain, Cursor's lock contention at twenty). They are not measured thresholds, and your breakpoints depend on the repo, the tasks and your checks.
              • pstack moves fast. Quotes are from the repository as of 23 October 2026 (version 0.15.32). Claude Code leaves auto-update off for third-party marketplaces, so a pstack install stays on the version you installed until you turn it on. Its README still says it was built at Cursor. Lauren Tan's GitHub profile now lists xAI, and her recent talk introduces her as working on Grok Bot. Since 0.15.24 Orchestrate no longer uses Graphite (gt): it walks the PR base chain itself, and Shipping and Babysit also say never to require it. Claude Code now installs a generated copy of pstack, and CI fails while that copy is out of date.
              • "Hundreds" is the sources' word. In her pstack guide (31 August 2026), Lauren Tan writes that you may get away with up to 10 agents in parallel with worktrees, and promises a later post on running hundreds of subagents in parallel in the cloud. Cursor reports runs that peak at several hundred agents. No source here gives an exact count for any one person's setup.
              • Company numbers are the companies' own. Stripe's and Spotify's figures are from their engineering blogs, Uber's from its engineering blog and AI Engineer World's Fair talk page, Kiro's from its own team, and Boris Cherny's from The Pragmatic Engineer's write-up of their interview. Block's are from an interview Anthropic published. None is independently measured.
              • Cost is real. Anthropic reports that its multi-agent research system used about 15 times the tokens of a chat. Claude Code's docs say agent teams use about 7 times the tokens of a standard session in plan mode. Measure before you scale.
              • The org layer is my synthesis. Its facts come from Claude and GitHub docs and from DORA's survey correlations. How the two org stages split the work, and their gates, are advice.
              • Limits change. The documented numbers below each stage are defaults as of October 2026. Check the linked docs before you plan around them.
