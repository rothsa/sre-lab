Running SLOs across thousands of services

    
    
      
  • Tier first. Give each service a tier and a default target per tier, so teams start from a number instead of a debate. Home Depot's SRE team proposed levels like this to product managers, with 99.9% “adequate for the majority of nonselling systems.”
    • 
      
  • Generate the rules. The rules above cover one service. For thousands, keep each SLO as a short spec and generate the recording and alert rules from a template. Sloth does this for Prometheus, reads OpenSLO, and aims for one uniform way to create SLOs across services and teams.
    • 
      
  • Count coverage. Track the share of services in each tier that have an SLO with a working alert. Once Home Depot automated collection, it went from about 50 services reporting SLOs to 800, with about 50 more registering each month.
    • 
      
  • Audit the policy. The Workbook's example policy halts changes other than P0 and security fixes while a service is out of budget, and requires a postmortem when one incident burns more than 20% of the budget in four weeks. Measure how often breaches actually led to both.
    • 
      
  • Freeze the org, agents included. When a shared platform runs out of budget, freeze every team that changes it; under the Workbook's policy, disputes go to the CTO. Agents that open PRs or roll out deploys are change too. Google's SRE team describes agents checking error budget status before they act, with agent-specific rate limits and circuit breakers.
    • 
      
  • People own the SLO. An agent can draft rules like these, but picking the SLI and the target is a product decision. Watch for an agent that “fixes” a noisy alert by raising a threshold or excluding an error class, and review SLO changes like code.
